# 发版流程与 Release 文案规范

Releases 页面是别人认识这个项目的第一屏。此前每版文案各写各的，
读的人分不清「这版动的是屏上那三页，还是浏览器里的面板」，
v0.9.5 甚至只剩一行自动生成的 Full Changelog。
现在统一成下面这套，历史版本已按同一口径回填。

## 一、标题：版本 · 范围 · 一句话

```
v0.9.6 · 面板 · 新增磁盘占用分析
└─版本─┘ └范围┘ └────一句话────┘
```

范围只有四个词，放在标题第二段，Releases 列表竖着扫下来能对齐：

| 范围 | 指什么 |
|:--|:--|
| `屏幕` | 屏上那三页的显示与交互 |
| `面板` | 浏览器里的管理后台（`http://<设备IP>:8080`） |
| `安装` | install.sh、依赖、部署、配置路径 |
| `工程` | 并发、测试、CI、重构这类看不见的改动 |

两侧都动了就写 `屏幕、面板`。一句话不超过 20 字，说改了什么，不写「若干优化」。

## 二、正文：像跟人说话

开头一两句说这版干了什么，然后一条一句列改动，需要时最后补一句怎么升级。

```markdown
# v0.9.6 · 面板 · 新增磁盘占用分析

面板左列多了一张"存储"卡，回答"这块盘到底被什么占满了"。

- 选一块盘，看一级目录 Top 8 和大文件 Top 10，带占比条。
- 这台机器上扫 932 GB 的机械盘用了 0.9 秒，所以直接同步扫，不用等后台任务。
- 用系统的 `du` 而不是自己遍历目录。媒体库里常有硬链接，自己算会把同一份数据算两遍。
```

小版本三五条就够，大版本到七八条。不必给每条配小标题，也不必按「新增 / 修复 / 变更」
分段，除非真的更好读。

## 三、别这么写

下面这些是之前踩过的坑，读起来像机器写的：

| 别写 | 改成 |
|:--|:--|
| 每段都用「——」接一句解释 | 短句说完，非补不可就另起一句 |
| 每段都加粗关键词 | 一条里最多一处，或者不加 |
| 用「不是 A，而是 B」讲道理 | 先说改了什么，理由只在真需要时说 |
| 收口、边角、根修、白花时间、凭空消失 | 改完、小问题、彻底修好、浪费时间、没了 |
| 「影响面：管理后台。屏幕的渲染与交互没有改动」 | 「只改了面板，屏幕没动」 |
| 拿比喻收尾，或补一句金句总结 | 写完就停 |

判断标准：这段话会不会在跟同事解释改动时说出口。不会，就重写。

## 四、发版顺序（这个顺序不能反）

1. `CHANGELOG.md` 写好本版段落，`grep -c "^## \[vX.Y.Z\]" CHANGELOG.md` 必须为 1。
2. 提交、推送 `master`，等 CI 绿灯。
3. 打 tag：`git tag -a vX.Y.Z -m "vX.Y.Z · <范围> · <摘要>"`。
4. **先建 Release 并写好正文，再推 tag**：`gh release create vX.Y.Z --title ... --notes-file ...`
   （此时 tag 还在本地，`gh` 会一并推上去）。
5. `git push origin vX.Y.Z`，CI 构建双架构并**只上传附件**。

第 4 步先于第 5 步的原因：CI 里 `action-gh-release` 一旦先跑，会先建出一个
空 Release（v0.9.5 的教训），之后补正文的窗口就被动了。CI 已去掉
`generate_release_notes`，不再覆盖正文，但「先写正文」仍是唯一稳妥的顺序。

## 五、发布后核对

```bash
gh release list --limit 3                     # 标题是否有「· 范围 ·」
gh release view vX.Y.Z --json body --jq '.body|length'   # 正文不为空
gh release view vX.Y.Z --json assets --jq '.assets|length'  # 应为 2
```

## 六、README 截图

屏幕三页用 `cmd/preview` 在真机上采样渲染（不是截屏），地址必须换成
RFC 5737 文档保留地址，由工具当场替换，不靠事后修图：

```bash
sudo ./preview -all -out /tmp/shot.png -version vX.Y.Z \
  -lan 192.168.1.10 -wan 203.0.113.42 -warm 30 -interval 2000
```

管理面板两张图在浏览器里截（1280 宽、DPR 2 → 输出 2560），浅色 / 深色各一张。
截图前必须处理三处，否则会把不该公开的东西留在图里：

1. **预览卡里的屏幕图换成 README 用的脱敏版。** 那张是实时重绘，带真实局域网
   与公网 IP。做法是克隆 `<img>` 节点、把 `src` 换成 `env.png` 的 data URI，
   再替换原节点——Vue 的轮询只更新已被移出 DOM 的旧节点，不会被刷回去。
2. **存储卡的大文件列表换成一行说明。** 单文件路径含私人文件名；一级目录名
   （媒体库、相机照片之类）可以留，那是「目录分析」，不指向具体内容。
3. **顶栏是 `position: sticky`，整页截图会在页面中部再画一次。**
   截图期间改成 `static`，否则图中会凭空多出一条导航栏。

另外容器列表的滚动区固定 300px、行高约 49.5px，直接截会切掉半行；
按真实行高收成 6 整行（inline `max-height`）再截。截完把底部纯背景的空白裁掉。

浏览器用 `playwright-core` + 本地缓存的 chrome-headless-shell，不必装整套 Playwright。
